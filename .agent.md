## 3. Build System Rules

### 3.1 Build Commands

**macOS (Apple Silicon / Intel):**
```bash
cmake -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_PREFIX_PATH=/opt/homebrew/opt/qt@5 \
  -DHamlib_INCLUDE_DIR=/opt/homebrew/include \
  -DHamlib_LIBRARY=/opt/homebrew/lib/libhamlib.dylib \
  -DPortaudio_INCLUDE_DIR=/opt/homebrew/include \
  -DPortaudio_LIBRARY=/opt/homebrew/lib/libportaudio.dylib \
  -DWSJT_GENERATE_DOCS=OFF \
  -S /path/to/wsjtx-polished -B build -G "Unix Makefiles"
cmake --build build -j$(sysctl -n hw.logicalcpu)
```

**Key points:**
- You **must** pass Qt5 prefix path via `CMAKE_PREFIX_PATH`
- Hamlib and PortAudio are found via explicit `_INCLUDE_DIR`/`_LIBRARY` hints when Homebrew is used
- Set `WSJT_SKIP_MAP65=ON` to skip PortAudio-dependent MAP65 sub-build
- macOS targets ≥10.13 (Intel) or ≥11.0 (ARM); deployment target is auto-detected from `uname -m`
- macOS builds link `libgomp.a` **statically** for deployable bundles
- Do **not** use `CMAKE_OSX_DEPLOYMENT_TARGET` unless you intend to produce an official installer

### 3.4 Compiler Flags

- **C++**: `-Werror -Wall -Wextra -fexceptions -frtti` (strict; warnings are errors)

- **Release**: `-fdata-sections -ffunction-sections` (non-Apple)
- **Visibility**: Hidden by default for all languages (`CMAKE_CXX_VISIBILITY_PRESET hidden`, etc.)

### 4.1 RX Data Flow

```
Sound Card → SoundInput → Detector (downsample ×4)
    → dec_data.d2[] (shared memory buffer)
    → jt9 process (Fortran, spawned subprocess): FFT → sync → decode → unpack
    → dec_data (shared memory, decoded messages)
    → MainWindow::guiUpdate() reads dec_data
    → DecodedText → display in WideGraph widget
    → (optional) PSKReporter spots, Logbook logging
```

### 4.2 TX Data Flow

```
User types message in MainWindow
    → Modulator::start(mode, symbols, ...)
    → Fortran gen_*wave() generates tone symbols
    → Modulator::readData() produces PCM audio frames
    → SoundOutput → Sound Card
    → (parallel) Transceiver keys PTT, sets frequency
```

### 4.3 Rig Control

```
MainWindow → TransceiverFactory → concrete Transceiver
    (runs in separate QThread)
    → HamlibTransceiver (via hamlib C library)
    → HRDTransceiver (via TCP to Ham Radio Deluxe)
    → DXLabSuiteCommanderTransceiver (via TCP)
    → OmniRigTransceiver (Windows COM, via dumpcpp)
    → TCITransceiver (via TCP, Expert Electronics protocol)
    → PollingTransceiver (periodic poll via Hamlib)
    → EmulateSplitTransceiver (split-mode emulation decorator)
```

## 5. Critical Files & Their Roles

### 5.1 THE Shared Structure (`commons.h`)

```c
struct dec_data {
  int   ipc[3];            // Inter-process communication flags
  float ss[184*NSMAX];     // Symbol spectra (184 symbols × 6827 bins)
  float savg[NSMAX];       // Average spectrum
  float sred[5760];        // Red average spectrum
  short int d2[NTMAX*RX_SAMPLE_RATE]; // RX audio buffer (30 min × 12000 Hz)
  struct {
    int nutc;              // UTC time as HHMM integer
    bool ndiskdat;         // true = reading from .wav file
    int ntrperiod;         // TR period in seconds
    int nQSOProgress;      // QSO state machine state
    int nfqso;             // QSO frequency (kHz offset)
    char mycall[12];       // My callsign
    char hiscall[12];      // DX callsign
    char mygrid[6];        // My grid square
    char hisgrid[6];       // DX grid square
    int nmode;             // Current mode
    int ntxmode;           // TX mode
    // ... ~60 more parameters ...
  } params;
};
```

**⚠️ CRITICAL**: This struct **MUST** stay in sync with `lib/jt9com.f90`. Any change to field order, type, or size in one file **must** be mirrored exactly in the other. Differences cause silent data corruption.

## 6. Design Patterns & Conventions

### 6.1 Patterns in Use

| Pattern | Where | Notes |
|---------|-------|-------|
| **pImpl** (pointer-to-implementation) | `pimpl_h.hpp`/`pimpl_impl.hpp` | Used by Configuration, Transceiver, and others for ABI stability and compile-time hiding |
| **Factory** | `TransceiverFactory` | Creates concrete Transceiver from enum |
| **Strategy** | Transceiver subclasses | Each implements rig-specific protocol |
| **Observer** (Qt signals/slots) | Everywhere | Thread-safe async communication |
| **Decorator** | `EmulateSplitTransceiver` | Wraps a Transceiver to emulate split operation |
| **Shared Memory** | `commons.h` dec_data, `shmem.cpp/.f90` | C++↔Fortran interop |
| **Subprocess** | `jt9` process spawned by MainWindow | Slow-mode decoder isolation |

### 6.2 Naming Conventions

| Language | Convention | Example |
|----------|-----------|---------|
| C++ classes | PascalCase | `MainWindow`, `HamlibTransceiver` |
| C++ files | PascalCase `.cpp`/`.hpp` | `Configuration.cpp`, `Radio.hpp` |
| C++ methods | camelCase | `setFrequency()`, `dataSink()` |
| Qt slots | camelCase | `on_pb160_clicked()` |
| C++ member vars | `m_` prefix | `m_config`, `m_ntx`, `m_decoderBusy` |
| C files | lowercase `.c`/`.h` | `init_random_seed.c`, `rs.h` |
| Fortran files | lowercase `.f90` | `ft8_decode.f90`, `jt9.f90` |
| Fortran modules | lowercase (sometimes with `_mod`) | `sfox_mod`, `ft8_params` |
| Fortran subroutines | lowercase | `subroutine ft8_decode()` |
| CMake vars | UPPER_SNAKE_CASE | `WSJT_GENERATE_DOCS` |
| CMake targets | lowercase_underscore | `wsjt_fort_omp`, `jt9` |
| `.pri` (qmake) files | lowercase | `widgets.pri`, `models.pri` |

### 6.3 Fortran-C++ Interop Rules

1. Fortran modules are compiled as **static libraries** and linked into the main executable
2. The `jt9` process is a **separate executable** spawned at runtime; it communicates via **shared memory** (`shmem.cpp/.f90`) and the `dec_data` struct
3. Fortran subroutines called from C++ use `extern "C"` declarations with **lowercase names + trailing underscore** (e.g., `four2a_()`)
4. The `C_interface_module.f90` provides ISO C Binding type aliases
5. `timer_C_wrapper.f90` wraps Fortran timing calls for C++ use
6. Array indices: **Fortran is 1-based**, C++ is 0-based — be very careful at boundaries

### 6.4 Threading Model

- **GUI thread**: MainWindow, all Qt widgets (main thread)
- **Rig control thread**: Each Transceiver runs in its own `QThread`
- **Decoder process**: `jt9` is a separate OS process, spawned/stopped by MainWindow
- **Decoder thread**: The main WSJT-X binary runs FT8/FT4/FST4/Q65 decoding on worker threads (via `QFuture`/`QtConcurrent`)
- **Network**: Qt's async networking (no explicit threads)
- **OpenMP**: Fortran DSP loops parallelized with OpenMP pragmas

## 8. Constraints & Hazards When Editing

### ⚠️ DO NOT (Hard Rules)

1. **NEVER** change `struct dec_data` in `commons.h` without mirroring the exact same change in `lib/jt9com.f90` — the two must be binary-identical
2. **NEVER** add source files without updating `CMakeLists.txt` — all sources are explicitly enumerated (no `file(GLOB ...)`)
3. **NEVER** use Qt6 APIs — this project targets **Qt 5** (Qt 5.12+); Qt6 port is a future task
4. **NEVER** introduce C++17 or later features — the codebase targets **C++11** and uses `-Werror`
5. **NEVER** change Fortran compiler from GNU gfortran without verifying OpenMP, FFTW3, and C interop work correctly
6. **NEVER** remove or reorder the `extern "C"` function declarations in `main.cpp` — they must match the Fortran symbol names exactly (lowercase + trailing underscore)
7. **NEVER** change `NSMAX` (6827) or `NTMAX` (30×60) in `commons.h` without understanding the buffer size implications throughout the entire codebase

### ⚠️ BE CAREFUL (Soft Rules)

1. `widgets/mainwindow.cpp` is ~5000+ lines — large refactors here are high-risk; prefer incremental changes
2. Fortran module build order matters; modules must be compiled before their consumers (CMakeLists.txt lists modules first in `wsjt_FSRCS`)
3. The `Configuration` class uses pImpl — add new settings fields to the private implementation, not the header
4. Adding a new digital mode requires: Fortran decoder, C++ integration in MainWindow, mode entry in Modes model, UI wiring, and potentially a new symbol set
5. The UDP message protocol uses big-endian format with magic `0xadbccbda` — any protocol changes must be versioned via the schema number
6. macOS bundles require explicit `install_name_tool` fixup for bundled dylibs (handled by `bundle_fixup/`)
7. Translations: English `.ts` file must always be included even if empty (prevents loading secondary language)

### ✅ PREFERRED PRACTICES

1. **New widgets**: Add to `widgets/` directory, list in both `CMakeLists.txt` and `widgets.pri`
2. **New dialogs**: Use Qt Designer `.ui` files; add to both `wsjtx_UISRCS` (CMake) and the `.pri` file
3. **New network service**: Follow the pattern in `Network/PSKReporter.cpp` (QNetworkAccessManager-based)
4. **Fortran changes**: Test with both `gfortran` and verify no new `-Wunused-dummy-argument` warnings
5. **Cross-platform**: Test on at least macOS and one other platform before submitting; Windows-specific code uses `#ifdef WIN32` guards
6. **Logging**: Use `BOOST_LOG_TRIVIAL` severity levels; production paths use `BOOST_LOG_FUNCTION`
